# UI and voice investigation

The MVP chooses **Rust business logic plus an Objective-C AppKit platform bridge**. It uses frameworks already installed with macOS and compiles with Apple's Command Line Tools. The initial offline build had no Cargo dependencies; optional OpenAI support now adds reqwest/rustls, serde/serde_json and zeroize. No JavaScript runtime or model download is needed. Rust owns command matching, subprocess bounds, API requests, bounded conversation history, runtime key ownership and explicit Keychain persistence, response/usage semantics, tests and the CLI. AppKit owns main-thread UI, the explicit secure settings dialog and platform audio state. The bridge copies Rust-owned JSON strings and frees them via the paired Rust allocator function.

GitHub's original language bar (Objective-C 63.1%, Rust 34.3%, Shell 2.6%) reflects source bytes. The committed tree contains 24,931 bytes in `.m`, 13,531 bytes in `.rs` including build.rs, and 1,012 bytes in `.sh`. Concrete AppKit layout, menus, text editing, window lifecycle, asynchronous authorization and Apple speech input/output require substantially more native glue than the original Rust command parser. This is genuinely a mixed-language app; the UI/audio portion is Objective-C, and compiling a Rust binary does not make that portion Rust. The new conversation/network/history/usage path is Rust. Direct Rust objc2 bindings could move that platform code later, but would not remove the AppKit lifecycle work.

The panel uses `NSPanel`, `NSFloatingWindowLevel`, and `hidesOnDeactivate = NO`; a menu-bar `NSStatusItem` supplies Show, Hide and Quit. This is a logged-in-user desktop app, not a headless system daemon. Hiding is explicit and reversible. No accessibility permission is needed by the app.

Other suitable Rust routes include eframe/egui, for a portable Rust UI, and Tauri, for a Rust backend with a web UI. Neither UI stack was cached on this Mac. eframe would need its crate/rendering stack; Tauri would add a web frontend build and dependencies. AppKit is the smallest native MVP here. A future character renderer could be embedded without changing the Rust command boundary. Direct Rust Objective-C bindings are another possible replacement for the bridge; the extra dependency is unnecessary for this first version.

Apple's native frameworks provide:

- **Output:** `AVSpeechSynthesizer`, selecting an available `AVSpeechSynthesisVoice` for `en-US`. It uses the system's installed voice, not the voice from this chat. No voice asset licensing or access is assumed.
- **Input:** `SFSpeechRecognizer` and `SFSpeechAudioBufferRecognitionRequest` with `AVAudioEngine`. Recognition must report on-device support, the request must require on-device recognition, and availability/permission failures must keep the microphone off. Apple notes that the request's local-only flag is only honored when on-device support is true; both gates are therefore required.
- **Permissions:** the bundle declares `NSSpeechRecognitionUsageDescription` and `NSMicrophoneUsageDescription`. Speech and microphone access are requested from the user-initiated flow; asynchronous callbacks return to the main queue. A generation counter invalidates canceled permission and recognition callbacks.

Speech support depends on OS, locale and installed assets. This MVP neither fetches missing assets nor enables a cloud fallback. Built-in macOS Dictation is a separate OS feature and is not controlled by this app. A future fully local recognizer such as whisper.cpp would need an explicitly selected model, download size, CPU/memory budget, license review and integration tests. A local conversation model likewise requires a real inference backend and weights; a command dispatcher is never labeled as AI.

On this Mac, initial requests failed with `kLSRErrorDomain 201` (“Siri and Dictation are disabled”), despite `supportsOnDeviceRecognition` returning true outside the execution sandbox. This was confirmed by Apple's `localspeechrecognition` service log and the installed SDK's `SFSpeechRecognitionTask.h` error table (201: Siri or Dictation disabled; 102: missing assets). Dan subsequently enabled system Dictation himself and reported transcripts appearing. The app displays native errors and app-scoped permission diagnostics. No system setting is automatically changed. See [Apple's user guide to Dictation](https://support.apple.com/guide/mac-help/use-dictation-mh40584/mac) for its location and the system's privacy explanation; system Dictation and Micah's strict device-only requests are distinct flows.

Speech results use a generation-checked transcript adapter. The UI disables Send/editing during capture and freezes the latest text on Stop. It synchronizes the NSTextField backing value and active field editor, then snapshots actual reviewed text for submission. Rust and synthetic AppKit self-tests cover command aliases/lifecycle; native tests request no audio permissions. Exact observed speech variants can be added as narrow aliases (`Max status` → `Mac status`); there is no fuzzy or arbitrary command execution. The result panel shows submitted text, matched route, source and API-reported usage. Optional AI receives only submitted non-command text and bounded successful AI turns. It never receives local status results or audio automatically.

The OpenAI path is user-controlled (including an explicit saved startup preference), text-only and stateless on the API (`store:false`, no previous response IDs). No tool dispatch, file attachment or repository reader exists. Session keys are entered by the user into an NSSecureTextField; the Rust owner uses Zeroizing<String>. The optional persistence adapter loads only Micah’s exact saved Keychain item on explicit Enable or saved startup opt-in; it never imports environment/file/other-app secrets. Non-secret settings alone use a mode-0600 JSON file. Verification runs suppress Keychain restoration. Requests and errors are not logged. [API testing evidence](API-TESTING.md) records fixture assumptions and the explicit absence of live paid verification.

## Local conversation turn detection

The optional session-only Conversation control keeps the existing device-only speech recognizer. A local PCM RMS gate (0.006 float full-scale) tracks sound activity; changed partial recognition text tracks transcript stability. Both must be quiet/stable for the selected 1.2/1.8/2.5 second interval before the current text is frozen and submitted once. Final recognition alone does not submit. This heuristic does not infer intent, identify a speaker or suppress all background noise.

Request dispatch and playback close capture. Completed playback schedules a generation-checked 650 ms delay before fresh capture; Stop, focus/visibility changes, failures, session expiry and turn limits invalidate pending rearm. Sessions are bounded to 3 minutes/10 turns, silence to 15 seconds, and an individual continuous utterance to 30 seconds. No wake word, background service capture, overlapping playback/capture, remote VAD or microphone upload is added. Auto-submit is off at launch and requires a disclosure plus a user click to start. Synthetic native tests intercept network and capture side effects to exercise the real pause/freeze/send/rearm lifecycle.
